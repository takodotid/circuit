# RouterOS 7 traps

- Every command takes effect as it arrives; there is no candidate configuration. `apply` saves a backup and arms a scheduler that restores it. A refused command restores the backup at once, which restarts the router: every session takes a minute or two to come back.
- `:put [:parse "..."]` compiles a command without running it and reports a syntax error or an unknown property. `apply` checks every command this way before the backup is taken. It does not catch:
    - the text inside `rule=`: a routing filter rule is checked only when it is added;
    - a quoted value, which passes whatever it is;
    - a `/system logging` rule whose action does not exist yet, refused with `input does not match any value of action`. The action is added first (CCR2216, 7.23.5).
- Output over SSH stops at 2 MiB, 2,097,152 bytes, mid-line and with no error. `/export`, plain or not, came back that long with 10,000 firewall rules, and with 20,000 and 40,000 NAT rules, and a `:put` after it in the same command never printed. `/export file=` wrote each whole, 2.8 MB to 5.7 MB, and SFTP fetched the file whole. So the read prints a mark after the export, and reads one without it again from a file. Writing and fetching the file take the `ftp` and `write` policies, which the groups `write` and `read` lack (CHR, 7.24.6).
- `find` matches nothing, silently, when:
    - a value with a slash is unquoted, `address=X/Y`;
    - a quoted `"yes"` meets a boolean, since it is a string;
    - a prefix is not whole. A route prints `dst-address=192.0.2.82/32` and an interface's address prints bare, `address=203.0.113.60`. Yet `find dst-address=192.0.2.82` and `find address=203.0.113.60` match nothing, while `"192.0.2.82/32"` and `"203.0.113.60/32"` match (RB5009, 7.24.6);
    - a list is not quoted with `;` between its items, even with one item: `topics="warning"` and `topics="script;debug"` match, `topics=warning` and `topics="script,debug"` do not (RB5009, 7.24.6).
- The plan quotes only values that are not plain words. A selector that matches nothing removes nothing, and the next `diff` shows what stayed.
- `~` in `find` has no anchors. Match exactly.
- `where comment!=""` also matches an entry without a comment: it counted 41 BGP connections that had none. `comment~"."` counts only those with one (CCR2216, 7.24.6).
- A property of the same group is printed as a bare suffix, `output.filter-chain=X .network=Y`, which only reads back inside that command. The parser expands it before building a `set`.
- A `/32` address gives no connected route, so a session over it never opens. Give the far end: `{ address, peer_address }` renders `network=<peer_address>`.
- `/routing bgp connection add` without `local.role` is refused, so the render always writes one. On 7.23 one without `instance` is refused too, `missing value(s) of argument(s) instance`, although the export never prints `instance=default`.
- A connection without `input.filter` accepts everything. A neighbor without a policy is given `REJECT-ALL`.
- A session edited repeatedly can stick, with SYN both ways, no RST, and no log. Remove the connection and add it again.
- A session that never established is missing from `/routing bgp session print`; look at `/routing bgp connection print`. One that is trying prints `established` empty, not `false`, and no uptime (7.23.5).
- A BGP session is named `<connection>-<n>`, and a renamed connection keeps its session's old name until the session restarts. `circuit bgp` matches a session by the neighbor's address first.
- A session closed on its limit keeps its entry with `limit-exceeded=true`, its `input.limit-process-routes`, and `last-stopped`. The notification it sent ends in `0601` (cease, maximum prefixes). Its `prefix-count` is back to 0, so the count that tripped it is gone. `/routing bgp session clear <id> flag=limit-exceeded` opens it again. A misspelled flag is a `syntax error`, and a `find` that matches nothing does nothing (CCR2216, 7.23.5).
- `time>` in a `/log print` filter does not filter. `circuit bgp --log` keeps the lines of the last minutes itself, against the device's clock.
- `tcp-md5-key` set from the CLI has been seen discarded without an error, and a mismatch logs nothing. Confirm with `/tool sniffer quick port=179`.
- Incoming GRE is subject to the input chain. Accept it before testing the tunnel.
- A WireGuard peer's name is unique on the device, and a new key under the same name is refused as a new peer: `entry with this name already exists`. The plan finds a peer by name, so a new key is a `set`.
- The export prints a WireGuard interface's `mtu=1420` although it is the default. Circuit counts it as the default (CCR2216, 7.24.6).
- `monitor-traffic` on a VLAN interface counts only what the CPU handles, and not consistently. Measure on the physical port, `/interface ethernet print stats`, which the switch chip counts.
- A VLAN interface on the bridge adds a dynamic bridge VLAN entry for its VLAN, "added by vlan on bridge", beside the static one. A selector by `vlan-ids` then finds both, and a `set` on the pair fails with `no such item`. Selectors on bridge VLANs skip dynamic entries.
- Any rule using fasttrack adds a dynamic "special dummy rule to show fasttrack counters" to the filter and the raw table. It cannot be removed, `cannot remove builtin`, so every selector over those menus skips dynamic entries.
- Switch-chip rules have no address lists and no connection state. A drop is an empty `new-dst-ports`.
- A switch-chip rule's `rate` does not limit traffic the CPU routes. Under a 12 Gbps flood, a rule at `2G` or `100M` changed nothing that reached the CPU, while a drop with the same match left 3 Mbps. Drop what you can recognize instead of limiting it (CCR2216, 7.23.5).
- The switch chip reads a UDP fragment after the first as port 0. When another rule drops a flood's first fragments by port, `src-port=0` drops the rest. Without it, the rest reach the CPU, which holds them while it waits for a first fragment that never comes.
- A switch-chip rule takes one port or a range, `1900-1901`; a list is refused. The render makes one rule for each port in a list.
- A switch rule the chip cannot hold is flagged `I`, invalid, and so is every rule after it, with no log line. On a CCR2216 (98DX8525, 7.23) this came at the sixth distinct `dst-port` range, at 66 rules. MikroTik lists 1,024. Distinct ranges run out, not rules: on 7.23.5, 70 rules with two distinct ranges were all valid. `validate` warns at more than 5 distinct ranges on a CCR2216. After a plan that changed switch rules, `apply` fails unless `print count-only where invalid` prints `0`.
- A switch rule matches a kind of frame with `mac-protocol` (`ip`, `ipv6`, `arp` among 23 kinds), but cannot match "not" one. So an ethertype filter is a rule that lets each kind through, then a last one with an empty `new-dst-ports` for the rest. These come after the port's ACL rules, which match only `ip` or `ipv6` (CCR2216, 7.23.5).
- No MAC learning limit on 7.23.5: `/interface bridge port` has `learn` but no limit, and `/interface ethernet switch port` has none (CCR2216). `mac_limit` stays refused.
- The connection table holds 1,048,576 entries on a CCR2216 with 16 GiB. A full table refuses every new connection through the router, not only the target's. A SYN flood of 210,000 packets a second filled it in five seconds. A UDP flood from random sources fills it about six times faster, because an unanswered UDP entry lives 30 seconds. Traffic in `untracked` prefixes never enters it.
- A `notrack` in the raw table also skips the reverse translation: a reply to a source NAT address inside an untracked block is never translated back. A raw `accept` for the address in each direction, before the `notrack`, keeps the address tracked (CCR2216, 7.23.5).
- With hardware offload on, routed traffic bypasses the forward chain entirely. `hardware_offload: false` on an interface makes the firewall apply to it, at the cost of CPU. The only proof of offload is the `H` flag on a route.
- A MACVLAN on a VLAN interface is not routed in the switch chip: its connected route never takes the `H` flag, even with `l3-hw-offloading=yes` on the VLAN under it.
- A static blackhole route prints `distance=1` in the export although 1 is the default; a route through a gateway at distance 1 prints none (CCR2216, 7.23.5). Circuit counts `distance=1` as the default on both.
- A bonding interface refuses a queue of its own that sets no rate: `/queue interface set <bond> queue=<cake type>` fails with `non rate limit queues are useless on this interface`, even with `cake-bandwidth` on the type. A queue tree with the bond as its parent takes the rule but sees no packet. So Circuit marks what leaves the interface in the mangle table's postrouting chain. A queue tree under `global` shapes the mark, with the rate as its `max-limit` and CAKE as its queue (CCR2216, 7.23.5).
- An EoIP tunnel gets a random `mac-address` when it is created, which the export prints. Circuit leaves it as the device made it. A bonding interface takes the MAC of its first member.
- A mangle rule's `passthrough=yes` is its default and the export leaves it out. One with `passthrough=no` ends its chain for what it matched: the rules after it counted nothing (CHR, 7.24.6).
- A mangle rule's `new-dscp` takes a number, 0 to 63: `new-dscp=ef` is a syntax error. `change-dscp` in the forward chain sets the DSCP of IPv4 and IPv6 packets alike. `set-priority` sets the PCP of the VLAN tag a packet leaves with, through a VLAN interface on a bridge with `vlan-filtering`: `/tool sniffer` on the next router printed priority 5 beside the VLAN ID, and its mangle rule with `ingress-priority=5` matched (CHR, 7.24.6).
- `/ping dscp=10` marks an IPv4 ping. An IPv6 ping still leaves with DSCP 0, so a test marks it in the mangle table's output chain instead (CHR, 7.24.6).
- `/ip cloud ddns-enabled` cannot be turned off on 7.23.5.
- `mac-server` and `mac-winbox` work at layer 2 and ignore the IP firewall; they are limited by interface list.
- `time-zone-autodetect` is on by default and wins after a restart. The render turns it off.
- The SSH client drops a password sent together with its newline. Send the password, wait, then the newline.
- A serial console login redraws lines unless the user name has `+cwt`.
- Narrowing a subnet is a change in several places: the address, the DHCP network, and every switch on the LAN. A mismatch breaks only the return path, so a test from the router passes.
- `strong-crypto=yes` also hardens the device's own SSH client, which then fails silently toward devices that only speak older algorithms.
- SNMPv3 authenticates with MD5 or SHA1 only on 7.23.
- `/snmp` sends every trap with one `trap-version` and one `trap-community`, the name of a `/snmp community` entry, which exists first. For version 3 that entry is the user. `trap-target` takes addresses only, so traps go to port 162. Out of the box `trap-generators` is `temp-exception`, so no trap reports a port going down (CCR2216, 7.24.6).
- In a quoted string `$` starts a variable. The adapter escapes it.
- A script sent over SSH exec runs as one line; a multi-line script fails with `expected closing brace`.
- `:find` on an array returns a number or `nil`. Globals persist between exec commands of one login.
- An empty array, `:local keep {}`, is a syntax error. A filter, NAT, or mangle table the config empties is removed chain by chain instead (RB5009, 7.24.6).
- A fixed port speed is named by medium, `speed=10G-baseSR-LR` for an optic or `speed=1G-baseT-full` for copper, and only stays set with `auto-negotiation=no`. With auto-negotiation back on, the export no longer prints the speed, so the plan resets only auto-negotiation. `speed=""` is refused as ambiguous and `unset speed` does not exist.
- `bgp-path-len` counts every AS in the path, prepends included, and takes the same strict comparisons as `dst-len`.
- `set bgp-path-prepend N` in an eBGP export filter sends the router's AS N times in all, not N more times: 1 changes nothing, and 16 sends 16 (CCR2216, 7.24.6).
- A `bgp-as-path` set with a space in it, `[174 64512-65534]`, is refused unquoted: `invalid bgp-as-path regexp`. Quoted inside the rule, `bgp-as-path \"[174 64512-65534]\"`, it is taken, and the export prints it as sent. A set takes ranges of 4-byte AS numbers: `/routing/filter/test-as-path-regexp` matched `[4200000000-4294967294]` against `64501,4200000001`, and not against `64501,4294967295` (CCR2216, 7.24.6).
- `/routing/filter/filter-wizard` adds the rule it builds; it is not a dry run. `set blackhole yes` was tested with it on 7.23.
- On the serial console, the prompt can come twice after a login. The console echoes a long command wrapped at 80 columns. A `print` that fills the screen stops at `-- [Q quit|D dump|down]`, where `D` prints the rest.
- Every VLAN interface on the bridge has the bridge's MAC, and the bridge keeps a frame to that MAC on whatever VLAN it arrives. So a gateway in front of a transparent firewall never gets its replies: they come back on the inside VLAN and stop at the bridge. A MACVLAN on the VLAN interface gives the gateway a MAC of its own, and its replies cross the firewall back.
- A second VLAN interface with the same VLAN ID on the same interface is refused with `already have such vlan`. So Circuit knows a VLAN interface by its interface and VLAN ID, and a new name is a rename.
- A name is unique in a menu, even where an entry is known by something else, such as a VLAN interface or a BGP connection. A new entry under a name the old one still has is refused. So Circuit changes a VLAN interface's VLAN ID with a `set`, and what points at it by name stays attached. It removes any other such entry before adding it again (CCR2216, 7.23.5).
- A VLAN interface on another is QinQ: the outer one adds its tag outside the inner one's. Removing a VLAN interface that another is on works, and leaves the other on nothing, `interface=*5`, with no error. So the plan removes the inner one first. `set interface=` moves a VLAN interface onto another, and `export` printed `c100` before `s300`, the VLAN interface it was on (CHR, 7.24.6).
- A bridge's `ether-type=0x88a8` (IEEE 802.1ad) is set on a running bridge, and is one TPID for all its ports. A frame tagged 0x8100 then counts as untagged: an access port with `frame-types=admit-only-untagged-and-priority-tagged` took such frames into its VLAN, their tag inside. A VLAN interface on the bridge took no frame until it had `use-service-tag=yes`, which a `set` changes in place. A VLAN interface with `use-service-tag=yes` on a port outside the bridge, made a bridge port to give that port 0x88a8 alone, carried nothing (CHR, 7.24.6).
- A CCR2216 with 12 active members in one LAG crash-looped, with a kernel failure each time LACP formed. RouterOS took the 12 in the config and failed only once more than 8 came up. `validate` refuses a LAG of more than 8 on a CCR2216.
- A LAG refuses a member that is a bridge port: `add` or `set slaves=` fails with `ether3 already in bridge`. So the plan removes the bridge port first. A bridge VLAN entry may name an interface that is no bridge port, flagged `ether4 not a bridge port`, so the VLAN entries can change after. The other way needs no order: the bridge takes a member of a LAG as a port at once, flagged inactive, `port is already slave`, and the port comes up once the LAG lets it go. A LAG needs a member: one with none is refused, `need at least one slave interface`. A bridge port on a LAG that is removed stays, as `interface=*9` (CHR, 7.24.6).
- `/ip neighbor` reports the far port in `interface-name`. From a Raisecom RAX721 and a FortiGate 3700D, it held the far port's description, not its name (CCR2216, 7.23.5). No other field holds the port. The reader maps a description to the far device's port when exactly one of its ports in the network has it.
- A neighbor's `interface` is a list: the port, then the LAG and the bridge it is in, `sfp28-1;infra-lag01-fwl;bridge`. Joined to a string in a script, a list repeats the whole line for each of its items. Use `:tostr` first.
- LLDP is only received on the interfaces in `discover-interface-list`. On a VLAN interface alone, such as the management one, a neighbor that sends untagged LLDP is never seen.
- A static route's `check-gateway` takes `arp`, `none`, or `ping` on 7.23.5, not `bfd`. A bare `bfd` is a syntax error. A quoted one passes `:parse`, then the run refuses it with `input does not match any value of check-gateway`. BFD on a static route stays refused.
- `/routing bfd configuration interfaces=all` does not cover a multihop session: its BFD session shows `BFD forbidden for destination address`. A configuration with the session's `addresses` makes it active. The render adds one for each multihop session with BFD.
- A BGP connection with `use-bfd=yes` stays Idle until its BFD session is up, so a peer that does not run BFD never comes up. A BGP session asks for BFD only once it has a session: a connection to an address that never answers shows no BFD session at all (CCR2216, 7.23.5).
- BFD timers never set print nothing, and a session then runs at `min-rx=200ms min-tx=200ms multiplier=5`, which print once set. The plan sets them back to those. A multihop BFD session that is down sends once a second whatever its timers.
- `use-bfd=no`, set on a connection that had `use-bfd=yes`, is printed by the export. It is the default, and the plan sets it to take BFD off.
- A routing table holds no routes the router forwards by unless it has `fib`: `/routing table add fib name=...`. The export prints the flag between the properties, `add comment=... fib name=...`.
- A BGP connection's `routing-table` is where the session installs what it learns, and where it announces from. An `output.network` prefix is announced only while that table has a route for it; a route in main alone is not enough. Learned routes there resolve their next hop through main. Routing filters cannot move a route to a table: `set routing-table` and `set table` are `invalid argument`. `validate` refuses a session in a table that holds none of `originated_prefixes`, and warns for each one the table lacks (CCR2216, 7.23.5).
- A running session takes a new `routing-table` only when it restarts, but its announcements stop at once. Until it restarts, it keeps its learned routes in the old table and announces nothing, even once the new table has the prefix. `/routing bgp session resend afi=ipv6` does not help (#157). So the plan disables the connection, waits until its session is gone from `/routing bgp session`, and enables it, and says so on the plan's line. After an apply, Circuit checks that each session still announces what it did before, unless the config stops it (CCR2216, 7.23.5).
- A connection's `disabled=no` sent right after its `disabled=yes` leaves the session running: its `last-started` does not change. Sent alone, `disabled=yes` closes the session within 0.1 s (CHR, 7.23.5 and 7.24.6, #263).
- A passive connection without `local.address` listens only on its default local address, `local.default-address`, which may be a public one. A peer connecting to another address of the router gets a TCP reset (CCR2216, 7.23.5).
- To a neighbor on a shared network, a passive connection without `local.address` listens on the router's address there, and the session comes up. With `multihop=yes`, it listened on the router's loopback, and refused a peer connecting to the router's address toward it. So `validate` refuses a passive multihop neighbor without `local_address` (CHR, 7.24.6).
- An eBGP connection without `multihop=yes`, to an address on no connected network, takes the TCP connection and logs `connection <local> from <remote>`. It then closes the TCP connection with no OPEN and nothing else in the log, even with `bgp,debug` logging on (CCR2216, 7.23.5). Without `local.address` it is flagged inactive instead: `cannot listen to incoming connections, missing 'local-address'` (CCR2216, 7.24.6). A passive one is too. With `local.address`, it refuses each connection with `EBGP peer is not on a shared network and multihop is not configured` (CHR, 7.24.6). So `validate` stops on an eBGP neighbor on no network the device shares, without `multihop`.
- A BGP connection whose `local.ttl` and `remote.ttl` were never set sends with TTL 255 and accepts any TTL: a session established with a neighbor whose packets arrive with TTL 1. MikroTik's reference says an unset `remote.ttl` takes `local.ttl`, 255, so that only a directly connected neighbor gets in; it does not. Once set, neither can be unset: `unset` does not offer them, and `local.ttl=""` is refused with `an integer required`. So the plan counts `local.ttl=255` and `remote.ttl=1` as the defaults, and takes a TTL check off with `remote.ttl=1` (CCR2216, 7.24.6).
- A connection with `remote.ttl=255` never establishes with a neighbor whose packets arrive with TTL 1. It still completes the TCP handshake, and answers the SYN with TTL 64 whatever its `local.ttl`. The neighbor's own side reaches Established for about 10 seconds at a time. With `remote.ttl=1`, the same neighbor established at once. This was tested between two connections on one router, whose packets keep the TTL they were sent with (CCR2216, 7.24.6).
- RouterOS 7 has no BGP aggregates: no `/routing bgp aggregate`, and no aggregate setting on a connection, template, or instance (CCR2216, 7.24.6).
- A connection's `output.default-originate` route goes through its `output.filter-chain`. Through a chain that rejects everything, nothing is sent. Once the chain accepts `dst==0.0.0.0/0`, the route goes out at once, without a restart. A default route learned over BGP is never announced without `default-originate`, even through a chain that accepts it. With `always` and a default route in the table, the session announced that route, with its AS path. So a session with `send_default_route` gets a chain of its own, which accepts the default route and then jumps to its export's chain. Set back to `never`, it prints in the export (CCR2216, 7.24.6).
- A connection's `hold-time`, `keepalive-time`, and `output.network` are cleared only with `unset`, one per command, and the export then prints none of them. Set empty, `hold-time` becomes `infinity`, `keepalive-time` is refused with `invalid time value`, and `output.network` prints as `""` (CHR, 7.23.5 and 7.24.6).
- The same holds for a connection's `multihop`, `afi`, `local.address`, and `input.limit-process-routes-*`. Set empty, `multihop` and the limits are refused, and `afi` and `local.address` print as `""`. Set to `no`, `multihop` prints. `connect` and `listen` refuse both an empty value and `unset` (`input does not match any value of value-name`). A new connection prints neither, and once set to `yes`, each prints (CHR, 7.23.5 and 7.24.6).
- `local.role=ibgp-rr` on a connection to another AS is taken, and the connection goes inactive: `invalid 'remote-as' and 'local-role' combination`. `validate` refuses a client in another AS. An instance's `cluster-id=""` is refused with `invalid value for argument cluster-id`, and `unset` clears it, so the plan unsets it (CCR2216, 7.24.6).
- A confederation is the instance's `as=<identifier>/<member AS>`, which the export prints as written. A connection refuses that form, `invalid value for argument as`. RouterOS breaks RFC 5065 with it: to an iBGP neighbor in its own member AS it sends the identifier in its OPEN, and takes the session only with `remote.as=<identifier>`. A neighbor in another member AS needs `remote.as=<member AS>/<identifier>`, in that order, with `local.role=ebgp`. It then gets the member AS in the OPEN, but the identifier in the AS path of each route, not an AS_CONFED_SEQUENCE. So Circuit refuses `routing.bgp.confederation`. Tested between two instances on one router (CCR2216, 7.24.6).
- A route reflector puts its own router ID on a reflected route as ORIGINATOR_ID. RFC 4456 has the BGP Identifier of the client the route came from. CLUSTER_LIST holds the reflector's `cluster-id` (CHR, 7.23.5 and 7.24.6).
- A connection whose `local.role` changes, such as from `ibgp-rr` to `ibgp`, restarts its session by itself (CHR, 7.24.6).
- Every BGP session offers graceful restart: `local.capabilities` holds `gr`. No property of a connection, template, or instance turns it on or off, and none makes a session reopen after `input.limit-process-routes-*` or only warn (CCR2216, 7.24.6).
- `/tool sniffer quick` left at a command's timeout runs until the login ends, and a second one in that login is refused: `already running`. `/tool sniffer packet` keeps what it caught, with each packet's `ttl` (CCR2216, 7.24.6).
- `/routing rule` is an ordered list without names, like a filter chain, and the plan rewrites it whole in the config's order. `lookup-only-in-table` drops a packet its table has no route for (a ping printed `no route`); `lookup` routes it by main instead. An interface to match is `interface=`. A `drop` or `unreachable` rule is printed with `!realm`, which Circuit does not write (CCR2216, 7.23.5).
- RouterOS 7.24 prints a service's sources as `available-from` and still takes `address`, which the render writes. The reader reads `available-from` as `address` (RB5009, 7.24.6).
- RouterOS 7.24 prints the default neighbor discovery entry as `set [ find default=yes ] advertise-dns=yes`, under `# automatic dns option advertising is not started`, on a device nobody changed it on. Circuit counts it as the default.
- Removing a PPPoE client before the interface list member that points to it leaves the member as `interface=*C list=*2000010`. So every `/interface` menu and `/ppp` sort near the start of the plan's order: added first, removed last.
- A static address that is the same as one a DHCP client holds is refused with `already have such address`. To move a port from a DHCP lease to the same address set by hand, the client goes first (RB5009, 7.24.6).
- An RB5009 has no serial console. `/system routerboard settings set enter-setup-on=delete-key` is taken and logged, but the setting is not there to print or read back. So its model says `serial_console: false` and the render leaves it out.
- A CHR has no `/system routerboard`: `bad command name routerboard`. Its model is `virtual`, so the render leaves `enter-setup-on` out (CHR, 7.24.6).
- A CHR prints `disable-running-check=no` on every port as it ships, though MikroTik's reference gives `yes` as the default. Circuit counts `no` as the default. The reference lists the property for CHR and x86 only, and the RB5009 and CCR2216 exports never printed it (CHR, 7.24.6).
- The first boot of a CHR from MikroTik's image makes a `/system keymat-provider` entry of its own, which the first `/export` leaves out. The next prints it, `add disabled=yes key-size=0 name=default qkd-cache-size=0 qkd-certificate=*0 type=qkd`, and so does a `print` or a REST read at once. It then goes by itself: within 20 s of a `print` on one CHR, after about two minutes on routers being set up, and not in six minutes of exports alone. After a restart it was gone. An `add` as printed is refused, `failure: QKD KME address is empty`, `find default=yes` is `bad parameter default`, and `set default` addresses it. So Circuit reads it as a setting, which the plan never adds or removes (CHR, 7.24.6).
- The default configuration of an RB5009 sets `/disk settings auto-media-interface=bridge`, sharing a USB disk on its bridge. Its default is `none`.
- A route with `disabled=yes` in the main table has no table at all. `get routing-table` is empty, so `find ... routing-table=main` misses it, and a `set` on it changes nothing, silently. A route with `disabled=yes` in another table keeps its table. A route selector in main is `(routing-table=main or !routing-table)` (RB5009, 7.24.6).
- One table holds several static routes to one prefix, told apart by their gateway, such as a backup through a second link at a higher distance. So the plan knows a route by its `dst-address`, `routing-table`, and `gateway`, and finds a blackhole route by `!gateway` (CCR2216, 7.24.6, #212).

The server keeps its binding after the client's Release: after `release`, or with the client disabled and enabled, a Solicit with the new hint got the old prefix, `binding exists`. The new hint took effect once the binding was gone: with the client disabled while the session came back, then enabled, or after `/ipv6 dhcp-server binding remove` and `release` (CHR, 7.24.6).
- A DHCP server with `use-radius=yes` asks RADIUS before each new lease: `User-Name` is the client's MAC in capitals, `52:54:00:00:0B:02`, with an empty `User-Password`, `Calling-Station-Id` its client ID, `1:52:54:0:0:b:2`, and `Called-Station-Id` the server's name. A reject logs `dhcp,error ... radius authentication failed ... access rejected`, and the client gets nothing and keeps asking. An accept gives a lease flagged `R`, whose time is the reply's `Session-Timeout`. Accounting Start and every `/ip dhcp-server config interim-update` an Interim-Update follow, with no byte counts. `/ip dhcp-server config` ships with `accounting=yes interim-update=0s radius-password=empty store-leases-disk=5m` (CHR, 7.24.6).
- A DHCPv6 server with `use-radius=yes` asks the RADIUS servers of `service=dhcp` before each new binding: `User-Name` is the MAC address in the client's DUID, in capitals, `52:54:00:00:0B:01`, with an empty `User-Password`, `Calling-Station-Id` the DUID in hex, `00030001525400000b01`, and `Called-Station-Id` the server's name. A reject logs `radius authentication failed for <DUID> PD: access rejected`, and the client gets no prefix. An accept with `Delegated-IPv6-Prefix` gives that prefix in place of one from `prefix-pool`, in a binding flagged `R` that lasts the reply's `Session-Timeout`. Accounting Start, Stop, and every `/ip dhcp-server config interim-update` an Interim-Update follow, as for DHCP. A client that asked for an address got one without `use-radius`, and none with it, twice, and RADIUS was never asked (CHR, 7.24.6).
- A CoA-Request and a Disconnect-Request from RADIUS for a DHCP lease or a DHCPv6 binding are answered with a NAK, `Error-Cause = Unsupported-Extension`, by `User-Name`, `Framed-IP-Address`, or both, and the lease stays (CHR, 7.24.6).
- A DHCP server that asks RADIUS about a request with Option 82 sends its circuit ID and remote ID as RFC 4679's `ADSL-Agent-Circuit-Id` and `ADSL-Agent-Remote-Id`, and as the attributes 96 and 97 of vendor 2352 too. A RouterOS relay with `add-relay-info=yes` puts the 6 bytes of its interface's MAC in the circuit ID, which FreeRADIUS prints as `0x525400000a03`, and the client's MAC in the remote ID. Its export then prints an empty `relay-info-remote-id=`. The server's accounting Start carries both IDs too, while its lease prints `agent-circuit-id=""` and `agent-remote-id=""`. The server took the relayed requests, which came in on its port toward the relay, with `relay=<the relay's address>`, which MikroTik's manual says it needs. A bridge has no `add-dhcp-option82` in 7.24.6, but `dhcp-agent-circuit-id`, and with `dhcp-snooping=yes` it dropped the server's offers toward a client, though its port to the server had `trusted=yes` (CHR, 7.24.6).
- An `/ip dhcp-relay` is added disabled, and the export then prints no `disabled`: a plan saw nothing to change while the relay relayed nothing. One turned on prints `disabled=no`, so the render writes it. An `/ipv6 dhcp-relay` is added turned on (CHR, 7.24.6).
- An interface's own `/ipv6 nd` entry wins over the default one: beside the default entry on, a port's entry with `ra-lifetime=none` gave a host that took its advertisements no default route, and the default entry alone gave one (CHR, 7.24.6).
- A PPP profile's `interface-list` adds each session's interface to that list while the session is up, as a dynamic member, `interface=<pppoe-subscriber>`, which the export leaves out. A list with a member of its own takes sessions too, and a firewall rule with `in-interface-list` matched a session's packets (CHR, 7.24.6).
- A PPP profile's `remote-ipv6-prefix-pool` gives each session a /64 of a pool with `prefix-length=64`, as a dynamic `/ipv6 nd prefix` on the session, `interface=<pppoe-subscriber>`, with a route to it. Only the default `/ipv6 nd` entry announces it: with that entry disabled, a session got no address, though another interface had an entry of its own. A RADIUS accept with `Framed-IPv6-Prefix` gives that /64 instead, with or without the pool, and accounting carries the /64 as `Framed-IPv6-Prefix`. `remote-ipv6-prefix-pool=""` clears it (CHR, 7.24.6).
- A router makes an address from router advertisements only with `/ipv6 settings accept-router-advertisements=yes`, as it forwards, and only on the interfaces of the list `accept-router-advertisements-on` names. An interface's own name there is refused: `input does not match any value`. It takes the default route the advertisements carry too, flagged `g`. After a change, the export prints `# ipv6 *accept router advertisements* configuration has changed, please restart device to apply settings`. A port taken down and up again still made no address, but a PPPoE session took the change when it next came up, and not before. Turned off, the session's address stayed until the session came up again (CHR, 7.24.6).
- A PPPoE client added to a VRF, or taken out of it, moves its session's address and routes at once, IPv6 and a delegated prefix's too. A VRF removed while it held the session left the address in it until the session came up again. A static route in the VRF with `gateway=<client>` stays inactive, `immediate-gw=""`, even once the session is up. With `gateway=<client>@<vrf>` it is active, and the export prints it as written. `/ip vrf` takes no VRF without an interface: `interfaces=""` is refused, `interfaces must be specified` (CHR, 7.24.6).
- Any static route in a VRF stays inactive, `immediate-gw=""`, unless its gateway ends in the VRF: `ether2@red`, `192.0.2.2@red`, `192.0.2.2%ether2@red`, `fe80::1%ether2@red`. Without it, a route through a port, a VLAN interface, a GRE or a WireGuard tunnel, or to an IPv4 or IPv6 next hop, with its interface or not, stayed inactive. With it, each was active and carried pings. MikroTik's manual says a gateway is looked up in main unless it says another table. `192.0.2.2@red%ether2` is taken and printed as `192.0.2.2%ether2@red`. The export prints a gateway as written, `find gateway=ether2` does not match `ether2@red`, and a route with `@red` is taken beside the same route without it (CHR, 7.24.6).
- A queue tree is HTB. Under load, every queue first gets its `limit-at`, and only then is what is left lent by `priority` (MikroTik's manual, HTB). Five classes over a parent of 400k showed it. When three priority-8 queues kept the whole rate in `limit-at`, two priority-1 queues without one sent nothing. When no queue had a `limit-at`, the priority-1 queues sent all they had, an EF ping took 33 ms, and the priority-8 queues shared alike, whatever their weights. When each priority-1 queue kept its cap as its `limit-at`, and the others their share of the rest, an EF ping took 8 ms, against 461 ms in a full best-effort queue. What a queue left unused went to the others alike, 53k each, not by their `limit-at` (CHR, 7.24.6).
- A queue tree leaf holds 10 packets, `queue=default-small`, the default `export verbose` prints with `priority=8`, `limit-at=0`, `bucket-size=0.1`, and no burst. A mark set in the mangle table's postrouting chain, by `out-interface`, reached a queue under `global` for a port, a VLAN interface, and a bonding interface alike. It reached it for the router's own pings and for IPv6 too. A mark with `passthrough=no` ends the chain for that packet (CHR, 7.24.6).
- `/tool traffic-generator start` is refused on a CHR as it ships: `not allowed by device-mode`. Turning device-mode on takes a power cycle, so a test sends with `/tool bandwidth-test` instead (CHR, 7.24.6).
- RouterOS 7 has an interface of its own named `lo`, `type="loopback"`, which `/interface print` lists. A loopback named `lo` is refused, `already have interface with name lo`. So `validate` refuses an interface named `lo` (CHR, 7.24.6).
- A queue type made with `kind=pfifo` holds 50 packets, and one made with `kind=red` takes `red-limit=60 red-min-threshold=10 red-max-threshold=50 red-burst=20 red-avg-packet=1000`. `export` leaves out each property at that value. `pfifo-limit` takes 1 to 4294967295. A RED type refuses a burst below its lower threshold, `RED burst smaller than min threshold`, an upper threshold not above the lower one, and a limit below the upper threshold. A queue type a queue tree uses can still be removed (CHR, 7.24.6).
- RED counts its queue in bytes, each threshold times `red-avg-packet`, though MikroTik's manual counts them in packets. Sent UDP at twice the rate, a queue with thresholds of 20 and 50 held about 50,000 bytes: 34 packets of 1500 bytes, or 100 of 500 bytes. With `red-avg-packet=1500` it held 50 packets of 1500 bytes. The average stayed near the upper threshold, so RouterOS drops seldom between the thresholds, and it has no setting for how often. A FIFO of 50 packets held 50, `default-small` 10. A RED queue's `queued-bytes` counts below 0, near 4294967296 (CHR, 7.24.6).
- Neither `priority` nor `max-limit` makes HTB lend spare bandwidth by share. Three queues kept 96k, 120k, and 24k of a 400k parent, its strict queues idle, and each was sent 400k. As Circuit writes them, they sent 147k, 174k, and 75k: the spare 160k went to them alike. Priorities 3, 2, and 4 gave all of it to priority 2: 96k, 280k, and 24k. A `max-limit` of 320k, 400k, and 80k changed little: 153k, 178k, and 67k. Only a `max-limit` of each one's share of the parent, 160k, 200k, and 40k, gave 159k, 200k, and 39k. But a `max-limit` holds a queue to it even when the others are idle: the queue with 80k sent 79k alone (CHR, 7.24.6).
- A routed packet's `ingress-priority` is the PCP of the VLAN tag it arrived with. A mangle rule matched it in each of the prerouting, forward, and postrouting chains. It did so for IPv4 and for IPv6. A packet that arrived without a tag has 0. Its `priority` stays 0, and it leaves through a VLAN interface with PCP 0, unless `set-priority` changes it. With `set-priority new-priority=from-ingress` in the forward chain, it left with PCP 5, as it came. A mark set in the postrouting chain by `ingress-priority=5` reached its queue under `global`, for IPv4 and IPv6 (CHR, 7.24.6).
- A bridge with `vlan-filtering=yes` passed a tagged frame between two ports with its PCP, 5, and its DSCP, EF, as they came. A bridge filter's `vlan-priority` is refused unless the rule has `mac-protocol=vlan`: `vlan matchers are valid only when mac-protocol is set to vlan or service-vlan` (CHR, 7.24.6).
- RouterOS has no policer with two rates (RFC 2698). A queue's `kind` takes `bfifo`, `pfifo`, `red`, `sfq`, `pcq`, `mq-pfifo`, `none`, `codel`, `fq-codel`, and `cake` (MikroTik's manual, queue type), and HTB shapes. A simple queue alone with `limit-at=0/100k max-limit=0/300k`, sent 600k, passed 300k, held 9 packets in its queue, and dropped the rest: `limit-at` only counts under a parent. The firewall's `limit` matcher polices one rate in bits: `limit=100k,12500:bit` in the mangle table's forward chain, with `action=drop` after it, passed 99k of 600k (CHR, 7.24.6).
- A PCQ queue type sorts IPv4 and IPv6 alike, each family by its own mask: `pcq-classifier=dst-address` with `pcq-dst-address-mask` and `pcq-dst-address6-mask`. `export` leaves out each property at its default: the masks at 32 and 128, `pcq-limit=50KiB`, `pcq-total-limit=2000KiB`, `pcq-burst-time=10s`, and the other bursts at 0. `pcq-rate=1.5M` prints as `1500k`, and `64000` as `64k`. A simple queue on a VLAN interface, `queue=<upload>/<download>` without `max-limit`, held two IPv4 addresses, sent 300k each, to its `pcq-rate` of 100k each: 98k, then 99k. Two IPv6 addresses in one /64, with a mask of 64, shared 100k: 24k, then 76k. One in another /64 had 99k. Each way: pulled from two sources, each got 98k. With a mask of 24, two addresses shared 100k: 78k, then 21k. A `max-limit` of 150k beside it held the two to 150k: 75k, then 74k (CHR, 7.24.6).
