# RouterOS 7 traps

- Every command takes effect as it arrives; there is no candidate configuration. `apply` saves a backup and arms a scheduler that restores it. A refused command restores the backup at once, which restarts the router: every session takes a minute or two to come back.
- `:put [:parse "..."]` compiles a command without running it and reports a syntax error or an unknown property. `apply` checks every command this way before the backup is taken. It does not catch:
    - the text inside `rule=`: a routing filter rule is checked only when it is added;
    - a quoted value, which passes whatever it is;
    - a `/system logging` rule whose action does not exist yet, refused with `input does not match any value of action`. The action is added first (CCR2216, 7.23.5).
- `find` matches nothing, silently, when:
    - a value with a slash is unquoted, `address=X/Y`;
    - a quoted `"yes"` meets a boolean, since it is a string;
    - a prefix is not whole. A route prints `dst-address=192.0.2.82/32` and an interface's address prints bare, `address=203.0.113.60`. Yet `find dst-address=192.0.2.82` and `find address=203.0.113.60` match nothing, while `"192.0.2.82/32"` and `"203.0.113.60/32"` match (RB5009, 7.24.6);
    - a list is not quoted with `;` between its items, even with one item: `topics="warning"` and `topics="script;debug"` match, `topics=warning` and `topics="script,debug"` do not (RB5009, 7.24.6).
- The plan quotes only values that are not plain words. A selector that matches nothing removes nothing, and the next `diff` shows what stayed.
- `~` in `find` has no anchors. Match exactly.
- `where comment!=""` also matches an entry without a comment: it counted 41 BGP connections that had none. `comment~"."` counts only those with one (CCR2216, 7.24.6).
- A property of the same group is printed as a bare suffix, `output.filter-chain=X .network=Y`, which only reads back inside that command. The parser expands it before building a `set`.
- A `/32` address gives no connected route, so a session over it never opens. Give the far end: `{ address, peer_address }` renders `network=<peer_address>`.
- `/routing bgp connection add` without `local.role` is refused, so the render always writes one. On 7.23 one without `instance` is refused too, `missing value(s) of argument(s) instance`, although the export never prints `instance=default`.
- A connection without `input.filter` accepts everything. A neighbor without a policy is given `REJECT-ALL`.
- A session edited repeatedly can stick, with SYN both ways, no RST, and no log. Remove the connection and add it again.
- A session that never established is missing from `/routing bgp session print`; look at `/routing bgp connection print`. One that is trying prints `established` empty, not `false`, and no uptime (7.23.5).
- A BGP session is named `<connection>-<n>`, and a renamed connection keeps its session's old name until the session restarts. `circuit bgp` matches a session by the neighbor's address first.
- A session closed on its limit keeps its entry with `limit-exceeded=true`, its `input.limit-process-routes`, and `last-stopped`. The notification it sent ends in `0601` (cease, maximum prefixes). Its `prefix-count` is back to 0, so the count that tripped it is gone. `/routing bgp session clear <id> flag=limit-exceeded` opens it again. A misspelled flag is a `syntax error`, and a `find` that matches nothing does nothing (CCR2216, 7.23.5).
- `time>` in a `/log print` filter does not filter. `circuit bgp --log` keeps the lines of the last minutes itself, against the device's clock.
- `tcp-md5-key` set from the CLI has been seen discarded without an error, and a mismatch logs nothing. Confirm with `/tool sniffer quick port=179`.
- Incoming GRE is subject to the input chain. Accept it before testing the tunnel.
- A WireGuard peer's name is unique on the device, and a new key under the same name is refused as a new peer: `entry with this name already exists`. The plan finds a peer by name, so a new key is a `set`.
- The export prints a WireGuard interface's `mtu=1420` although it is the default. Circuit counts it as the default (CCR2216, 7.24.6).
- `monitor-traffic` on a VLAN interface counts only what the CPU handles, and not consistently. Measure on the physical port, `/interface ethernet print stats`, which the switch chip counts.
- A VLAN interface on the bridge adds a dynamic bridge VLAN entry for its VLAN, "added by vlan on bridge", beside the static one. A selector by `vlan-ids` then finds both, and a `set` on the pair fails with `no such item`. Selectors on bridge VLANs skip dynamic entries.
- Any rule using fasttrack adds a dynamic "special dummy rule to show fasttrack counters" to the filter and the raw table. It cannot be removed, `cannot remove builtin`, so every selector over those menus skips dynamic entries.
- Switch-chip rules have no address lists and no connection state. A drop is an empty `new-dst-ports`.
- A switch-chip rule's `rate` does not limit traffic the CPU routes. Under a 12 Gbps flood, a rule at `2G` or `100M` changed nothing that reached the CPU, while a drop with the same match left 3 Mbps. Drop what you can recognize instead of limiting it (CCR2216, 7.23.5).
- The switch chip reads a UDP fragment after the first as port 0. When another rule drops a flood's first fragments by port, `src-port=0` drops the rest. Without it, the rest reach the CPU, which holds them while it waits for a first fragment that never comes.
- A switch-chip rule takes one port or a range, `1900-1901`; a list is refused. The render makes one rule for each port in a list.
- A switch rule the chip cannot hold is flagged `I`, invalid, and so is every rule after it, with no log line. On a CCR2216 (98DX8525, 7.23) this came at the sixth distinct `dst-port` range, at 66 rules. MikroTik lists 1,024. Distinct ranges run out, not rules: on 7.23.5, 70 rules with two distinct ranges were all valid. `validate` warns at more than 5 distinct ranges on a CCR2216. After a plan that changed switch rules, `apply` fails unless `print count-only where invalid` prints `0`.
- A switch rule matches a kind of frame with `mac-protocol` (`ip`, `ipv6`, `arp` among 23 kinds), but cannot match "not" one. So an ethertype filter is a rule that lets each kind through, then a last one with an empty `new-dst-ports` for the rest. These come after the port's ACL rules, which match only `ip` or `ipv6` (CCR2216, 7.23.5).
- No MAC learning limit on 7.23.5: `/interface bridge port` has `learn` but no limit, and `/interface ethernet switch port` has none (CCR2216). `mac_limit` stays refused.
- The connection table holds 1,048,576 entries on a CCR2216 with 16 GiB. A full table refuses every new connection through the router, not only the target's. A SYN flood of 210,000 packets a second filled it in five seconds. A UDP flood from random sources fills it about six times faster, because an unanswered UDP entry lives 30 seconds. Traffic in `untracked` prefixes never enters it.
- A `notrack` in the raw table also skips the reverse translation: a reply to a source NAT address inside an untracked block is never translated back. A raw `accept` for the address in each direction, before the `notrack`, keeps the address tracked (CCR2216, 7.23.5).
- With hardware offload on, routed traffic bypasses the forward chain entirely. `hardware_offload: false` on an interface makes the firewall apply to it, at the cost of CPU. The only proof of offload is the `H` flag on a route.
- A MACVLAN on a VLAN interface is not routed in the switch chip: its connected route never takes the `H` flag, even with `l3-hw-offloading=yes` on the VLAN under it.
- A static blackhole route prints `distance=1` in the export although 1 is the default; a route through a gateway at distance 1 prints none (CCR2216, 7.23.5). Circuit counts `distance=1` as the default on both.
- A bonding interface refuses a queue of its own that sets no rate: `/queue interface set <bond> queue=<cake type>` fails with `non rate limit queues are useless on this interface`, even with `cake-bandwidth` on the type. A queue tree with the bond as its parent takes the rule but sees no packet. So Circuit marks what leaves the interface in the mangle table's postrouting chain. A queue tree under `global` shapes the mark, with the rate as its `max-limit` and CAKE as its queue (CCR2216, 7.23.5).
- An EoIP tunnel gets a random `mac-address` when it is created, which the export prints. Circuit leaves it as the device made it. A bonding interface takes the MAC of its first member.
- A mangle rule's `passthrough=yes` is its default and the export leaves it out.
- `/ip cloud ddns-enabled` cannot be turned off on 7.23.5.
- `mac-server` and `mac-winbox` work at layer 2 and ignore the IP firewall; they are limited by interface list.
- `time-zone-autodetect` is on by default and wins after a restart. The render turns it off.
- The SSH client drops a password sent together with its newline. Send the password, wait, then the newline.
- A serial console login redraws lines unless the user name has `+cwt`.
- Narrowing a subnet is a change in several places: the address, the DHCP network, and every switch on the LAN. A mismatch breaks only the return path, so a test from the router passes.
- `strong-crypto=yes` also hardens the device's own SSH client, which then fails silently toward devices that only speak older algorithms.
- SNMPv3 authenticates with MD5 or SHA1 only on 7.23.
- In a quoted string `$` starts a variable. The adapter escapes it.
- A script sent over SSH exec runs as one line; a multi-line script fails with `expected closing brace`.
- `:find` on an array returns a number or `nil`. Globals persist between exec commands of one login.
- An empty array, `:local keep {}`, is a syntax error. A filter, NAT, or mangle table the config empties is removed chain by chain instead (RB5009, 7.24.6).
- A fixed port speed is named by medium, `speed=10G-baseSR-LR` for an optic or `speed=1G-baseT-full` for copper, and only stays set with `auto-negotiation=no`. With auto-negotiation back on, the export no longer prints the speed, so the plan resets only auto-negotiation. `speed=""` is refused as ambiguous and `unset speed` does not exist.
- `bgp-path-len` counts every AS in the path, prepends included, and takes the same strict comparisons as `dst-len`.
- `/routing/filter/filter-wizard` adds the rule it builds; it is not a dry run. `set blackhole yes` was tested with it on 7.23.
- On the serial console, the prompt can come twice after a login. The console echoes a long command wrapped at 80 columns. A `print` that fills the screen stops at `-- [Q quit|D dump|down]`, where `D` prints the rest.
- Every VLAN interface on the bridge has the bridge's MAC, and the bridge keeps a frame to that MAC on whatever VLAN it arrives. So a gateway in front of a transparent firewall never gets its replies: they come back on the inside VLAN and stop at the bridge. A MACVLAN on the VLAN interface gives the gateway a MAC of its own, and its replies cross the firewall back.
- A second VLAN interface with the same VLAN ID on the same interface is refused with `already have such vlan`. So Circuit knows a VLAN interface by its interface and VLAN ID, and a new name is a rename.
- A name is unique in a menu, even where an entry is known by something else, such as a VLAN interface or a BGP connection. A new entry under a name the old one still has is refused. So Circuit changes a VLAN interface's VLAN ID with a `set`, and what points at it by name stays attached. It removes any other such entry before adding it again (CCR2216, 7.23.5).
- A CCR2216 with 12 active members in one LAG crash-looped, with a kernel failure each time LACP formed. RouterOS took the 12 in the config and failed only once more than 8 came up. `validate` refuses a LAG of more than 8 on a CCR2216.
- `/ip neighbor` reports the far port in `interface-name`. From a Raisecom RAX721 and a FortiGate 3700D, it held the far port's description, not its name (CCR2216, 7.23.5). No other field holds the port. The reader maps a description to the far device's port when exactly one of its ports in the network has it.
- A neighbor's `interface` is a list: the port, then the LAG and the bridge it is in, `sfp28-1;infra-lag01-fwl;bridge`. Joined to a string in a script, a list repeats the whole line for each of its items. Use `:tostr` first.
- LLDP is only received on the interfaces in `discover-interface-list`. On a VLAN interface alone, such as the management one, a neighbor that sends untagged LLDP is never seen.
- A static route's `check-gateway` takes `arp`, `none`, or `ping` on 7.23.5, not `bfd`. A bare `bfd` is a syntax error. A quoted one passes `:parse`, then the run refuses it with `input does not match any value of check-gateway`. BFD on a static route stays refused.
- `/routing bfd configuration interfaces=all` does not cover a multihop session: its BFD session shows `BFD forbidden for destination address`. A configuration with the session's `addresses` makes it active. The render adds one for each multihop session with BFD.
- A BGP connection with `use-bfd=yes` stays Idle until its BFD session is up, so a peer that does not run BFD never comes up. A BGP session asks for BFD only once it has a session: a connection to an address that never answers shows no BFD session at all (CCR2216, 7.23.5).
- BFD timers never set print nothing, and a session then runs at `min-rx=200ms min-tx=200ms multiplier=5`, which print once set. The plan sets them back to those. A multihop BFD session that is down sends once a second whatever its timers.
- `use-bfd=no`, set on a connection that had `use-bfd=yes`, is printed by the export. It is the default, and the plan sets it to take BFD off.
- A routing table holds no routes the router forwards by unless it has `fib`: `/routing table add fib name=...`. The export prints the flag between the properties, `add comment=... fib name=...`.
- A BGP connection's `routing-table` is where the session installs what it learns, and where it announces from. An `output.network` prefix is announced only while that table has a route for it; a route in main alone is not enough. Learned routes there resolve their next hop through main. Routing filters cannot move a route to a table: `set routing-table` and `set table` are `invalid argument`. `validate` refuses a session in a table that holds none of `originated_prefixes`, and warns for each one the table lacks (CCR2216, 7.23.5).
- A running session takes a new `routing-table` only when it restarts, but its announcements stop at once. Until it restarts, it keeps its learned routes in the old table and announces nothing, even once the new table has the prefix. `/routing bgp session resend afi=ipv6` does not help (#157). So the plan disables and enables the connection, and says so on the plan's line. After an apply, Circuit checks that every session still announces what it announced of `originated_prefixes` before (CCR2216, 7.23.5).
- A passive connection without `local.address` listens only on its default local address, `local.default-address`, which may be a public one. A peer connecting to another address of the router gets a TCP reset (CCR2216, 7.23.5).
- An eBGP connection without `multihop=yes`, to an address on no connected network, takes the TCP connection and logs `connection <local> from <remote>`. It then closes the TCP connection with no OPEN and nothing else in the log, even with `bgp,debug` logging on (CCR2216, 7.23.5). Without `local.address` it is flagged inactive instead: `cannot listen to incoming connections, missing 'local-address'` (CCR2216, 7.24.6).
- A BGP connection whose `local.ttl` and `remote.ttl` were never set sends with TTL 255 and accepts any TTL: a session established with a neighbor whose packets arrive with TTL 1. MikroTik's reference says an unset `remote.ttl` takes `local.ttl`, 255, so that only a directly connected neighbor gets in; it does not. Once set, neither can be unset: `unset` does not offer them, and `local.ttl=""` is refused with `an integer required`. So the plan counts `local.ttl=255` and `remote.ttl=1` as the defaults, and takes a TTL check off with `remote.ttl=1` (CCR2216, 7.24.6).
- A connection with `remote.ttl=255` never establishes with a neighbor whose packets arrive with TTL 1. It still completes the TCP handshake, and answers the SYN with TTL 64 whatever its `local.ttl`. The neighbor's own side reaches Established for about 10 seconds at a time. With `remote.ttl=1`, the same neighbor established at once. This was tested between two connections on one router, whose packets keep the TTL they were sent with (CCR2216, 7.24.6).
- RouterOS 7 has no BGP aggregates: no `/routing bgp aggregate`, and no aggregate setting on a connection, template, or instance (CCR2216, 7.24.6).
- A connection's `output.default-originate` route goes through its `output.filter-chain`. Through a chain that rejects everything, nothing is sent. Once the chain accepts `dst==0.0.0.0/0`, the route goes out at once, without a restart. A default route learned over BGP is never announced without `default-originate`, even through a chain that accepts it. With `always` and a default route in the table, the session announced that route, with its AS path. So a session with `send_default_route` gets a chain of its own, which accepts the default route and then jumps to its export's chain. Set back to `never`, it prints in the export (CCR2216, 7.24.6).
- `/tool sniffer quick` left at a command's timeout runs until the login ends, and a second one in that login is refused: `already running`. `/tool sniffer packet` keeps what it caught, with each packet's `ttl` (CCR2216, 7.24.6).
- `/routing rule` is an ordered list without names, like a filter chain, and the plan rewrites it whole in the config's order. `lookup-only-in-table` drops a packet its table has no route for (a ping printed `no route`); `lookup` routes it by main instead. An interface to match is `interface=`. A `drop` or `unreachable` rule is printed with `!realm`, which Circuit does not write (CCR2216, 7.23.5).
- RouterOS 7.24 prints a service's sources as `available-from` and still takes `address`, which the render writes. The reader reads `available-from` as `address` (RB5009, 7.24.6).
- RouterOS 7.24 prints the default neighbor discovery entry as `set [ find default=yes ] advertise-dns=yes`, under `# automatic dns option advertising is not started`, on a device nobody changed it on. Circuit counts it as the default.
- Removing a PPPoE client before the interface list member that points to it leaves the member as `interface=*C list=*2000010`. So every `/interface` menu and `/ppp` sort near the start of the plan's order: added first, removed last.
- A static address that is the same as one a DHCP client holds is refused with `already have such address`. To move a port from a DHCP lease to the same address set by hand, the client goes first (RB5009, 7.24.6).
- An RB5009 has no serial console. `/system routerboard settings set enter-setup-on=delete-key` is taken and logged, but the setting is not there to print or read back. So its model says `serial_console: false` and the render leaves it out.
- The default configuration of an RB5009 sets `/disk settings auto-media-interface=bridge`, sharing a USB disk on its bridge. Its default is `none`.
- A route with `disabled=yes` in the main table has no table at all. `get routing-table` is empty, so `find ... routing-table=main` misses it, and a `set` on it changes nothing, silently. A route with `disabled=yes` in another table keeps its table. A route selector in main is `(routing-table=main or !routing-table)` (RB5009, 7.24.6).
- One table holds several static routes to one prefix, told apart by their gateway, such as a backup through a second link at a higher distance. So the plan knows a route by its `dst-address`, `routing-table`, and `gateway`, and finds a blackhole route by `!gateway` (CCR2216, 7.24.6, #212).
- RouterOS prints `::ffff:0:0/96` as `::ffff:0.0.0.0/96`, the IPv4-mapped form of RFC 5952. Adding `::ffff:0:0/96` again is refused, `already have such entry`, so the plan compares addresses in one spelling (CHR, 7.24.6).
- A route's gateway can carry its interface, `gateway="fe80::1%vlan10"` or `gateway="192.0.2.1%vlan10"`. The device takes it quoted and prints it bare in `export`, and a quoted `find gateway="fe80::1%vlan10"` matches it (CCR2216, 7.24.6).
- Once a user has an SSH key, RouterOS refuses that user's password over SSH: `/ip ssh password-authentication` is `yes-if-no-key` by default. Circuit logs in by password, so its next login fails with `login failure`. The render sets `password-authentication=yes` when any user has a key. There is no `always-allow-password-login` on 7.24 (RB5009, 7.24.6).
- `/user export` leaves SSH keys out, and the device never prints a key back. `/user ssh-keys print` shows `fingerprint=SHA256:...` (SHA-256 of the key, base64 with its padding) and the key's comment as `info`. The reader lists keys by fingerprint and the plan compares by it; `find user=... and fingerprint="SHA256:..."` matches (RB5009, 7.24.6).
- A DHCP client added without a name is called `client1`, `client2`, and so on. One named after its port, `name=ether1`, is taken. The export prints `default-route-tables=wan1:1,main:200` bare. The plan knows a client by its interface and changes it in place, since one set by hand may have another name and a script (RB5009, 7.24.6).
- To the plan, a bridge whose `vlan-filtering` changes is another bridge. It removes the bridge and adds it again, which drops every port on it. An apply that does that over the bridge's own LAN cannot send its next command. The RB5009's defconf bridge was switched to VLAN filtering by hand before the first apply (7.24.6).
