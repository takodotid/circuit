# Platforms

| `platform`     | OS                | Version    | Tested on                                                                          |
| -------------- | ----------------- | ---------- | ---------------------------------------------------------------------------------- |
| `routeros`     | MikroTik RouterOS | 7          | CCR2216-1G-12XS-2XQ, RouterOS 7.23; RB5009UG+S+, RouterOS 7.24; CHR, RouterOS 7.24 |
| `vrp`          | Huawei VRP        | V200R005   | CE6855-48S6Q-HI, V200R005C00SPC800                                                 |
| `raisecom-ros` | Raisecom ROS      | 6.5        | RAX721-C-6C48, ROS 6.5.2                                                           |
| `junos`        | Juniper Junos     | 21.3, 21.4 | QFX5100-48S-6Q, Junos 21.4R3                                                       |
| `fortios`      | Fortinet FortiOS  | 6.2        | FG-3700D, FortiOS 6.2.2                                                            |

- **One version per platform.** `routeros` means RouterOS 7. RouterOS 6 takes other commands, so Circuit doesn't support it.
- **Version check.** On RouterOS, Junos, and FortiOS, `diff` and `apply` stop if the device runs another version. VRP and Raisecom ROS don't check, so check the version yourself before the first apply.
- **Only the models it was tested on.** Another model needs its port list added. See [Contributing](/contributing).
- **Model limits.** On the CCR2216, a LAG holds at most 8 ports, and the hardware ACLs hold about 5 different port ranges. `circuit validate` checks both. The RB5009 has no serial console, so Circuit refuses `connection.console` on it.
- **CHR.** MikroTik's Cloud Hosted Router is RouterOS in a virtual machine. Its ports are the machine's network adapters, as many as it has: `virtual-1` is `ether1`, and so on. Circuit disables every adapter the config leaves out.
- **A RouterOS PPPoE server.** Subscribers live in RADIUS. Before the first `apply` on a router that already serves PPPoE, move every subscriber from `/ppp secret` to RADIUS: the plan removes each local secret, PPP profile, and PPPoE server that `services.pppoe_server` doesn't write, and sets the profiles `default` and `default-encryption` back to RouterOS's defaults. A prefix RADIUS sends (`Delegated-IPv6-Prefix`) needs no setting: the session delegates it, with or without `prefix_delegation`.
- **A FortiOS PPPoE client.** It is an entry of `system pppoe-interface` in root, which makes an interface named after the client over its port, LAG, or VLAN interface. The interface takes no default route from the server: write a static route through it. FortiOS 6.2 takes no IPv6 static route through it. Its config was applied, read back, changed, and removed on a FortiGate, but no session came up there, so it stays experimental.
- **FortiOS OSPF and IS-IS.** FortiOS 6.2 has no cost for an OSPF range, which takes the largest cost inside it. A point-to-multipoint link with `neighbors` needs `cost`, which each neighbor takes. FortiOS's NBMA and point-to-multipoint links say hello every 30 seconds unless set, so write `hello_interval` and `dead_interval` on both ends when the other runs another platform. FortiOS 6.2 runs OSPFv3 in the default VRF only, so OSPF in a VRF is for IPv4. IS-IS leaks level 2 routes into level 1 through an access list, which matches no prefix length. A FortiGate took the leak, but no IS-IS neighbor sent it a route to leak, so it stays experimental.
- **A RouterOS DHCP server with `radius`.** RouterOS asks RADIUS with the client's MAC address in capitals as `User-Name`, such as `52:54:00:00:0B:02`, and an empty password, so the RADIUS server lets a client in by its MAC address alone. A lease lasts the `Session-Timeout` of the server's accept when it has one. A DHCPv6 server asks with the MAC address in the client's DUID, in capitals too, such as `52:54:00:00:0B:01`, and a prefix the accept sends (`Delegated-IPv6-Prefix`) replaces one from `prefix_delegation`. It asks about delegated prefixes only, and gives no address while it asks, so Circuit refuses `radius` beside `pool` there. All the DHCP and DHCPv6 servers that have `radius` share one list of RADIUS servers and one `acct_interim_interval`. A request a relay added Option 82 to (RFC 3046) reaches RADIUS with its circuit ID and remote ID, as RFC 4679's `Agent-Circuit-Id` and `Agent-Remote-Id`, so RADIUS may accept a home by its line. A RouterOS relay with `relay_agent_information` puts the 6 bytes of its interface's MAC address in the circuit ID, which FreeRADIUS prints as `0x525400000a03`, and the client's MAC address in the remote ID. RouterOS answers a change of authorization or a disconnect for a lease with a NAK.
- **VRP.** A CloudEngine filters with ACLs on its ports, so write hardware ACLs. Circuit refuses the firewall's chains there: the switch's traffic filter checks what it switches as well as what it routes, V200R005 filters traffic to the switch only with a blacklist, and nothing filters what the switch sends. A DHCP server is an address pool, and nothing on the switch ties it to its interface. A DHCPv6 server's pool is the smallest prefix that holds its addresses, and leaves the rest of the prefix out, 1024 addresses at most. IS-IS is one process, `isis 1`, on VLAN interfaces. A point-to-point link sends one hello for both levels, which VRP signs with one key, so it refuses a key for each level beside a point-to-point link. On an NBMA or point-to-multipoint link, VRP says hello every 30 seconds and waits 120 for one, where a broadcast link takes 10 and 40: the other routers on the link need the same. A point-to-multipoint link finds its neighbors by multicast, so VRP refuses its `neighbors`. A CE6855 routes a port only on a VLAN from a range the switch reserves for routed ports, which Circuit has no key for, so a routed link is a VLAN interface. A VLAN interface there ends no inner VLAN, and a bridge domain binds one VLAN, none with a VLAN interface, so VRP builds neither.
- **RouterOS and 802.1ad.** Every switched port is on one bridge, whose `ether-type` is one TPID for all of them. So `tpid: "0x88a8"` goes on every switched port and LAG, or on none. A frame with an 802.1Q tag then counts as untagged on each port: an access port takes it into its VLAN, with its tag inside, as a QinQ port does. Circuit refuses DHCP snooping, RA guard, `stp: false`, `ethertypes`, hardware ACLs, and pseudowires beside it, as none was tried on such a bridge. A VLAN interface with `inner_vlan_id` is a VLAN interface on the outer VLAN's. That is the outer VLAN's plain VLAN interface when there is one, or else one Circuit adds, named after the VLAN.
- **RouterOS EVPN.** RouterOS 7.24 runs EVPN over VXLAN only: no EVPN over MPLS, no EVPN-VPWS, and no multihoming of its own. Its EVPN routes carry VNI 0, so the VTEPs tell one segment's routes from another's by their route targets alone: give each segment targets of its own. It announces no IP address beside a MAC address, no IP prefix (type 5 routes), and no route for its own VLAN interfaces, which the far VTEPs reach by flooding. A neighbor that carries `l2vpn-evpn` carries nothing else there.
- **VRP EVPN.** Experimental: a CE6855 on V200R005 committed it, but no far VTEP came up. Each segment is a bridge domain numbered by its VNI and bound to its VLAN, with its EVPN instance, and `interface Nve1` sends every segment from the address of the VTEP to the VTEPs that BGP finds. The switch takes a VNI up to 16000000. The address of the VTEP is a VLAN interface's, which is up only while a port of its VLAN is, or a loopback's, which no switch has tried as a VTEP. No VLAN interface routes a segment's VLAN. A session that carries `l2vpn-evpn` alone exchanges no IPv4 routes, and V200R005 resets a session as it starts or stops carrying EVPN routes. A segment's route distinguisher can't change in one apply: the switch takes a new one only once the old is gone, so remove the segment in one apply and add it in the next.
- **VRP MPLS.** Experimental: a CE6855 on V200R005 committed LDP on VLAN interfaces, but no LDP session came up. VRP labels host routes only unless told, so Circuit has it label every route, as LDP does elsewhere, the management network's too. An LDP policy is a prefix list for the labels the switch gives: V200R005 has none for the labels it takes, and takes a policy for every neighbor or for some, not both. Huawei's guide says MPLS doesn't run beside a MUX VLAN, so Circuit refuses MPLS beside a private VLAN. Huawei's guide also says a CloudEngine switch can't be a PE, and the CE6855 has no RSVP-TE, pseudowires, or VPLS.
- **Junos EVPN.** Experimental: Juniper documents EVPN-VXLAN on a QFX5100 as a VTEP that bridges its VXLAN segments and routes none, and the switch here took it in `commit check` without the `evpn-vxlan` and `vxlan` licenses it lacks. Circuit writes it in the default switch, one EVPN instance with one route distinguisher, so a QFX5100 takes one segment. The segment starts from the main loopback's one IPv4 address, needs one import and one export target, and no VLAN interface routes its VLAN. A neighbor that carries `l2vpn-evpn` may carry `ipv4` or `ipv6` beside it, and its policies see those routes only.
- **RouterOS RSVP-TE.** A tunnel carries the pseudowires whose far PE is its `destination`, those BGP sets up for a VPLS too, and nothing else: routes and an L3VPN's traffic keep to LDP and the IGP, and no route can point into a tunnel. CSPF reads OSPF's traffic engineering, and IS-IS carries none, so beside IS-IS a tunnel needs `explicit_path`, and takes no `admin_groups`. RouterOS keeps a tunnel's priorities and record route on its paths alone, so Circuit writes them on each path of the tunnel. It sets up ahead one secondary path, the first that comes up, so `standby` goes on the first secondary path. A tunnel on a secondary path tries its primary path again about every 30 seconds. A tunnel that goes down keeps its pseudowires, whose frames are lost until it is up again. Turning OSPF's traffic engineering off crashed the routing process each way it was tried, so Circuit doesn't do it: the plan stops and says why. RouterOS has no fast reroute and no link or node protection. Junos refuses RSVP-TE while its MPLS is experimental.
- **RouterOS IS-IS on both levels.** A router on both levels leaks every level 2 route into level 1, and its filter chain held none back, so Circuit refuses `level2_to_level1` there, and `circuit validate` warns about `level_capability: "level-1-2"`. The level 1 routers behind it got no default route from it either.
- **Raisecom ROS.** The switch answers time queries whenever it takes time from `system.ntp`, and nothing stops it, so write `services.ntp_server`, or `validate` warns. BPDU guard is one setting for the whole switch, and the switch finds edge ports by itself: with `bpdu_guard`, write `edge` on each port that runs spanning tree. A switch's SSH key belongs to no user, so SSH keys wait. A hardware ACL is an IPv4 list and an IPv6 list, named after it with `-v4` and `-v6`, so its name takes 29 characters at most. A rule there matches one TCP or UDP port, so write each port of a range, and each list ends with a rule that lets the rest through. IP source guard is one setting for the whole switch, which drops IP on every port not trusted, so Circuit doesn't bind a port to hosts there. Private VLANs are experimental: the switch took them, but no frame crossed it. So is ARP inspection, which turns on for every port at once, so a switch in service only parsed it. A DHCP server is a pool, named after it in 16 characters at most, served on a VLAN interface, with two DNS servers at most and a lease in whole minutes. It and a DHCP relay are experimental, as no client has asked one for an address yet. The switch answers NETCONF on port 830 whatever is set, which Circuit doesn't manage yet. A loopback forms no OSPF adjacency and takes no OSPF setting there: write it as `{}`. A RAX721 restarted minutes after a plan removed an OSPF process in a VRF, with no cause in its log, so Circuit refuses OSPF in a VRF and sends OSPF's newer settings and uRPF with `--experimental` only. BGP carries IPv4 in the main table, and a route-map's name and a prefix list's take 20 characters at most. BGP, its route policies, and IS-IS's leak into level 1 are experimental: the switch took them, but no session came up and no route crossed a route-map. Graceful restart there has only its timers, so Circuit refuses it.

## Feature matrix

The table comes from Circuit's code, not from datasheets. [Standards](/reference/standards) lists the RFC behind each feature.

| Mark | Means                                                                                                                                                               |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ✅   | Works, and tested on a real device.                                                                                                                                 |
| ❌   | Not on this platform, or not built yet. Circuit stops you.                                                                                                          |
| 🧪   | Built from the vendor's documentation, but not tested on a real device yet. Circuit stops, unless you add `--experimental`. Then it's a warning, and yours to test. |

A note in a cell means "works, with this limit".

FortiOS refuses `rate_limit.per_prefix`. Its per-IP shaper counts every packet of a session, both ways, against the address that started the session, so a session started from outside would count against the far end, not the customer.

A FortiOS tunnel matches `remote_identity` against each part of the subject of the peer's certificate, whole: `CN=branch-1` doesn't take `CN=branch-10`.

A route-based tunnel in a VRF on FortiOS has its interface, its addresses, and the routes through it in the VRF, while IKE and ESP leave from `local_address` in the table that holds it. RouterOS runs IKE in the main table only, so a policy-based tunnel there takes no VRF.

On Junos, GTSM is a session's `ttl 255` and a term of the loopback's filter that drops BGP from the neighbor when it arrives with another TTL or hop limit. A QFX5100 took both in `commit check`, on single-hop eBGP sessions only. Juniper doesn't say whether the loopback's filter sees the TTL a packet arrived with or one less, so GTSM stays experimental there.

On Junos, policy routing is Juniper's filter-based forwarding, experimental: a QFX5100 took it in `commit check`. A table is a `virtual-router` routing instance without interfaces, as the switch has no `forwarding` instance. A RIB group puts the main table's interface routes in each table, so a table's routes reach their next hops, and the networks the switch is on stay reachable from it. A filter of each family sends what a rule matches to its table. It sits on each VLAN interface, routed port, and tunnel of the main table with an address of the family, so the switch policy-routes what it routes, not what it sends itself. A table whose rules fall back to main does so through a default route to the main table, so the table takes no default route of its own, and its rules all fall back alike. Junos puts no BGP session's routes in a table, and refuses policy routing beside `qos.marking` or a routed port's `ingress_acl`, as an interface takes one filter of each family.

Policy-based IPsec:

- **RouterOS.** The IKE daemon has no AES-GCM, and runs in the main table only, so a tunnel's `local_address` is outside every VRF. It takes a peer's certificate that any certificate it holds signed, so `ca_certificate` must be its only certificate without a private key. It has no setting for ESP in UDP without a NAT, or for the NAT keepalive interval, and asks a silent peer again every 5 seconds, whatever the interval says. It matches the peer's identity by the ID the peer sends, never by a certificate's subject, and only when the peer starts IKE: as the end that starts it, it takes the peer whatever identity it expects. So a policy-based tunnel takes none of these yet, nor `remote_identity`.
- **FortiOS.** A policy-based tunnel is a phase 1 without an interface, a phase 2 for each traffic selector, and a firewall policy with `action ipsec` for each, which sends the selector's traffic into the tunnel and lets the far end's in. The policies come before those of `firewall.filter.forward`, so they take the selectors' traffic whatever the forward chain says. FortiOS 6.2 takes such a policy only with named interfaces: its `srcintf` is each interface whose network holds the local prefix or lies inside it, or that a static route inside it leaves through, so a local prefix needs one. 6.2 runs policy-based tunnels for IPv4 only: write a route-based tunnel for IPv6.
- **Junos, VRP, Raisecom ROS.** The switches don't encrypt what they forward.

IPsec remote access is built on RouterOS and FortiOS:

- **RouterOS.** One remote access on a router, beside no `fast_path` rule, whose flows skip IPsec's policies. It takes one traffic selector: it narrows a client that asks for all its traffic to the first alone. As for a policy-based tunnel, IKE has no AES-GCM and runs in the main table only, and `ca_certificate` must be the router's only certificate without a private key. RouterOS gives a client the selectors as the subnets of its configuration payload too. Its RADIUS servers for EAP may be in a VRF.
- **FortiOS.** A dial-up phase 1, `type dynamic` with `mode-cfg`, and a phase 2 for its one traffic selector, both of the remote access's name, in root. The device narrows a client that asks for all its traffic to the selector. A client connects only once a firewall policy accepts traffic from the tunnel, so `firewall.filter.forward` must accept the clients' traffic, by the pool's addresses. FortiOS 6.2 gives three DNS servers at most, and takes the name of a remote access as its interface's, 15 characters at most. With certificates, the `user peer` of the CA takes the clients. With EAP, the RADIUS servers are one entry of the remote access's name, with an accounting server for each, in a user group of its name and `-users`. FortiOS 6.2 has no VRF for a RADIUS server, and sometimes leaves an accounting server's port out of what it prints, so Circuit refuses `acct_port`. EAP is experimental: no RADIUS server was in reach of the test, so no client logged in with it.
- **Junos, VRP, Raisecom ROS.** The switches don't encrypt what they forward.

No platform writes IKEv1. RFC 9395 deprecates it.

Marking is refused on RouterOS beside a `fast_path` rule, and with `system.hardware_offload` unless the rule matches a VLAN interface with `hardware_offload: false` in `in_interface` or `out_interface`: traffic on the fast path or offloaded skips it. On the other platforms:

- **Junos.** Marking is a filter for each family, `circuit-marking` and `circuit-marking-v6`, on each VLAN interface, routed port, and tunnel where routed packets arrive. A term for each rule sets the DSCP, and the forwarding class of its `class`. The switch sorts a packet into its class as it arrives, so a rule that sets a DSCP also sets the class of that DSCP. The filter sees what the switch receives itself too, which changes nothing it sends. It can't see the interface a packet leaves through, and a routed port with an `ingress_acl` takes no second filter. A QFX5100 sets a PCP only with a rewrite rule on the port a packet leaves through, for every packet of a class, the ones it switches too, so Junos refuses `pcp`. Matching by `in_interface` is not built. Marking stays experimental: a QFX5100 passed `commit check` with it, but nothing was committed.
- **FortiOS.** Marking is by session, not by packet. Each rule is a shaping policy, and the first one that matches a session's first packet marks every packet of the session that goes the same way. The replies keep their DSCP. The policy also gives the session its class: the rule's `class`, or the class of the DSCP it sets. FortiOS 6.2 sets a PCP only in a firewall policy, so it refuses `pcp`. A session takes one shaping policy, so FortiOS refuses marking beside a `rate_limit`, which uses them too. It refuses marking with `system.hardware_offload` or a `fast_path` rule: write `system.hardware_offload: false`, which turns offload off on each policy that accepts. No offloaded session was seen marked.
- **VRP.** Marking is Huawei's MQC: an ACL and a traffic classifier for each rule, and a traffic policy for each family, applied to all the switch receives. Huawei's reference has `remark dscp` work only on what the switch routes, as marking means. `remark 8021p` works only on what it switches, so VRP refuses `pcp`. A rule that gives a `class` has a behavior of its own, which sets the class's queue with `remark local-precedence`. A CE6855 took the policies on a spare port, but no packet was seen marked, so marking stays experimental.

- **FortiOS.** A DSCP is set for a whole session, in the firewall policy or the shaping policy the session takes. A session takes one shaping policy, and rate limits already use them.
- **Raisecom ROS.** Not built yet.

NAT64 and DNS64 are built on FortiOS only:

- **FortiOS.** NAT64 is on for the whole VDOM, with one NAT64 prefix, a /96, which DNS64 uses too. Each rule is a NAT64 policy, which also lets its traffic through: FortiOS checks NAT64 traffic against NAT64 policies alone, not against the forward chain, and `validate` warns when the forward chain has rules. Its DNS server is DNS64 whenever NAT64 is on, so beside a `nat64` rule, `dns_server` needs `dns64`. Both are experimental: a FG-3700D took the config, but no traffic crossed it.
- **RouterOS.** MikroTik's NAT page says RouterOS does not support NAT64, and its DNS server has no DNS64. A CHR with 7.24.6 has no setting for either.
- **Junos.** A QFX5100 has no NAT: Juniper's Feature Explorer lists none for it on 21.4. NAT64 runs on SRX firewalls and on MX routers with a services card.
- **VRP.** Circuit builds no NAT there. Huawei's FAQ on NAT in CloudEngine switches gives it to the CE12800 with a firewall card only, and Huawei builds NAT64 on NE routers with a CGN board.
- **Raisecom ROS.** Circuit builds no firewall there, and no DNS server.

On FortiOS a TCP MSS clamp is the `tcp-mss` of the interface its `if.in_interface` names. FortiOS 6.2 lowers the MSS of each SYN and SYN-ACK that arrives on that interface, of both families, and leaves one that offers less as it is. So a clamp there names its interface alone, with a number of bytes, not `path_mtu`, and the clamps of one interface agree.

FortiOS refuses a deterministic CGNAT pool. FortiOS 6.2's pool of `type fixed-port-range` gives each subscriber of a pool address an equal share of the ports from 5117 to 65532, with no setting for the first port or the size of a share, so its shares are not `port_set_size` ports from 1024. Fortinet's fixed port range algorithm also gives a port past a full share, so `circuit nat lookup` couldn't always find a port's subscriber. Fortinet's 7.0.1 CLI reference has `startport` and `port-per-user`.

Option 82 on a DHCP relay is proven on RouterOS. Two platforms build it, but no request relayed through them has shown what they add:

- **Junos.** `relay-option-82 circuit-id` in the relay's group. The circuit ID is the port and its VLAN, and there is no remote ID. No QFX5100 has tried it.
- **FortiOS.** `dhcp-relay-agent-option` on the interface. A FortiGate relay adds Option 82 unless told not to, so without `relay_agent_information` Circuit writes `disable`. A FG-3700D took the setting both ways, and each change and removal left an empty plan, but no request was relayed. Fortinet's documentation doesn't say what the circuit ID holds.

A DHCP server for a relay's clients is built on RouterOS, and experimental on Junos and VRP. Junos and VRP pick the pool whose network holds the relay's address, so each refuses a `relay` outside `network`. On Junos the servers of one interface share one group, as a QFX5100 fails a second group on an interface in `commit check`. A QFX5100 took a pool for a relay's clients beside one for its own in `commit check`, but no relayed request reached it. On VRP it is a pool for the clients' network, as any DHCP server is there: a CE6855 committed one for a network none of its interfaces has, but no relayed request reached it. FortiOS serves a relay's clients from a server on the interface their requests come in on, with the network behind the relay. FortiOS 6.2 answers a relayed request from the server whose network holds the relay's address, `giaddr`, so it refuses a `relay` outside `network`, and answers each relay in `network` alike: the setting for the relay's own address comes in 7.4, as `relay-agent`. A client on that interface itself gets no address from such a server. Raisecom ROS builds neither.

A scheduler on RouterOS needs its `rate`, and each strict queue its `max`. RouterOS queues with HTB, which gives each queue the rate it keeps for it first, then lends what is left by priority. So a strict queue keeps its `max` and goes first, and a weighted queue keeps its share of the rate less the strict queues' `max`. What a weighted queue leaves unused goes to the other weighted queues alike, not by share. A priority for each weighted queue gives it all to one, and a cap at each share leaves the link idle when the other queues are. A marking rule's `class` is a packet mark of the class's name, which the scheduler of each interface moves into its queue before it looks at the DSCP. A class's `pcp` is RouterOS's ingress priority, the PCP of the VLAN tag a packet arrived with, which the scheduler looks at after the DSCP. A scheduler is refused on a switched port, whose routed packets leave through the VLAN interface. It is refused beside a `fast_path` rule, and with `system.hardware_offload` unless on a VLAN interface with `hardware_offload: false`, as packets there skip the queues. Raisecom ROS doesn't build classes and schedulers yet.

Junos writes a forwarding class for each class, its queue its place in `qos.classes`, so a QFX5100 takes 8 classes at most. The switch sorts a packet as it arrives, with classifiers named `circuit` on each port and LAG: one by DSCP, which lists all 64, and one by PCP. Once a port has a DSCP classifier, the switch sorts an IP packet by its DSCP alone, so a DSCP no class lists can't fall back to its PCP. So Junos sorts by DSCP or by PCP, not both. By PCP, a port without tags sorts every packet as PCP 0, and a trunk sorts IP by its PCP too. A scheduler is a scheduler map of its name, on each port and LAG that takes it: a strict queue is `strict-high`, its `max` a `shaping-rate`, and a weighted queue's `share` its `transmit-rate` in percent, which also weighs what the queues share. The switch doesn't shape a port, so Junos refuses `rate`. Juniper doesn't document several strict queues as taking turns on a QFX5100, so a scheduler takes one. On a LAG the switch shapes each member, so a strict queue there has no `max`. A VLAN interface has no queues of its own: write the scheduler on its ports. Broadcast, multicast, and flooded frames leave from a queue of their own, `mcast`, which no class holds, and `validate` warns about it. All of it is experimental: a QFX5100 passed `commit check`, and change and removal each left an empty plan, but nothing was committed.

On VRP, a port has 8 queues, so a device has 8 classes at most. `default_class` takes queue 0, and the other classes take queue 1 and on, in the order `qos.classes` lists them. A DiffServ domain of Circuit's own, `circuit`, puts each DSCP or PCP into its class's queue, and every port trusts it. A port trusts the DSCP when a class other than the default lists one, and the PCP otherwise. It can't trust the DSCP and then the PCP, so VRP refuses classes that list both. Circuit puts every PCP in the default class's queue there, for a packet without a DSCP, such as ARP. Every port keeps the PCP a packet arrives with: the switch would otherwise write the PCP from the queue. A scheduler is on a port: the strict queue is PQ, capped at its `max`, the weighted queues are DRR with their `share` as weights, and `rate` is the port's `qos lr`. The switch sends its strict queues in order, the highest first, where Circuit's take turns, so a scheduler has one strict queue at most. A port without a scheduler sends its queues as the switch does by default: all by PQ, the highest queue first, so the class written last goes first there. A marking rule that writes a DSCP also sets the queue of the class of that DSCP, as the switch sorted the packet by the DSCP it arrived with. VRP refuses a scheduler on a LAG or a VLAN interface, and classes beside a LAG: no Eth-Trunk has taken the trust settings. Classes, schedulers, and a marking rule's `class` are experimental: a CE6855 took them on a spare port, with no packet in a queue.

FortiOS sorts sessions, not packets. Each DSCP a class lists is a shaping policy of each family, after the marking rules, and the first that matches a session's first packet gives every packet of the session its class, both ways. The firewall's own traffic matches no shaping policy, so it takes `default_class`. A class is a traffic class, numbered from 2 in the order `qos.classes` lists them, so FortiOS 6.2 takes 30 classes. A scheduler is a shaping profile of its name that queues, and the interface's `outbandwidth` is the scheduler's `rate`, which FortiOS needs. A strict queue is priority `top` and keeps its `max`, which FortiOS needs, as a whole percent of the rate. A weighted queue is priority `low` and keeps its share of what the strict queues leave, rounded down to a whole percent. Fortinet's handbook lends what the queues leave unused by priority, and at one priority by what each queue keeps. FortiOS 6.2 matches no PCP in a shaping policy, so it refuses classes by PCP. It refuses classes beside a `rate_limit`, as a session takes one shaping policy. Fortinet's 6.2.1 release notes list bug 469798: an egress shaping profile doesn't shape offloaded traffic. So FortiOS refuses a scheduler with `system.hardware_offload` or a `fast_path` rule: write `system.hardware_offload: false`, which turns offload off on each policy that accepts.

A queue with `depth_packets` takes a queue type of its own on RouterOS: a FIFO of that many packets, or RED. RouterOS's RED counts bytes, not packets, so Circuit counts a packet as 1500 bytes: a queue of full-size packets holds `depth_packets`, and one of smaller packets holds more of them. The thresholds of RED are rounded down to whole packets, and RouterOS refuses two that come to the same number. RouterOS has no setting for how often RED drops between its thresholds. VRP refuses `depth_packets`, and so `red`, which needs it: V200R005 sets no depth for a queue. A QFX5100 gives a queue a part of its port's buffer, in percent of the bytes, and its RED counts in percent of that, so Junos refuses both. On FortiOS a queue's depth is its shaping entry's `limit`, 5 to 10000 packets, and 1000 without `depth_packets`. FortiOS's RED drops up to a set share of the packets at the upper threshold, `red-probability`, which Circuit has no key for, so FortiOS refuses `red`.

Policing with two rates, RFC 2698's two-rate three-color marker, is built on no platform. RouterOS has none: a queue's `limit-at` and `max-limit` shape with HTB, holding what comes above them, and the firewall's `limit` matcher polices one rate. The other platforms don't build it yet.

Trust for each port, whether a port keeps the DSCP or PCP a packet arrives with, is built on no platform. On VRP, every port trusts the classes the same way, as said above. RouterOS keeps a routed packet's DSCP unless a marking rule changes it, and sends it with PCP 0 unless a marking rule sets one. Its bridge passes both as they came. RouterOS has trust settings only in the switch chip of some CRS3xx, CRS5xx, CCR2116, and CCR2216 models, from 7.15, which a CHR lacks, so no test can prove them.
